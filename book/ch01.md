# 1. Hello, Wolf

<p class="epigraph">Bruckner's Fourth opens with one horn call over a
tremolo — everything the symphony will do, said once, quietly, before
anyone explains it.</p>

## 1.1 A program worth keeping

Books like this one open with a program that prints a greeting. That
program is in this chapter too, and you should type it. First, though, a
program you might keep.

You have a file of rows: a name, a comma, an amount in cents. The
question is what they add up to.

```wolf,run(exit=0)
fn main() -> !int {
    let rows = """
        espresso,340
        pastry,275
        tip,100
        """
    var total = 0
    for row in rows.lines() {
        var i = 0
        while row[i..i + 1] != "," { i += 1 }
        let name = row[..i]
        let cents = row[i + 1..].to_int() else 0
        total += cents
        print("{name:<10}{cents:>6}")
    }
    print("{"total":<10}{total:>6}")
    0
}
```

It answers:

```console
$ lupin receipt.lu
espresso     340
pastry       275
tip          100
total        715
```

Eighteen lines, and nothing in them is a preview of syntax you meet
later — this is the language. `let` names a value; `var` names one that
changes. `"""` opens a block literal whose common indentation is trimmed
away, so the data sits where you would put it in a file. Braces inside a
string interpolate the expression between them, and `{cents:>6}` means
right-align in six columns. `row[..i]` slices bytes. `for` walks what
`lines()` hands it.

Two lines lie for convenience. The `while` loop trusts every row to hold
a comma, and `else 0` decides that an amount which is not a number is
worth nothing. §1.5 shows what the first lie does when the input
disagrees, and chapter 6 takes both apart; this program is Part 1's
running example, and it gets more honest in every chapter.

Now the greeting. The smallest wolf program that does anything:

```wolf,run(exit=0, stdout="hello, wolf")
fn main() -> !int {
    print("hello, wolf")
    0
}
```

`main` is where a program starts. `print` writes one line to standard
output. The `0` on its own line is the value `main` returns, and the
process exit code — §1.3 makes that concrete. The `!` in `!int` says
`main` may fail instead; chapter 6 is where that becomes a tool, and
until then it is the shape `main` has.

No imports, no enclosing class, no guard against being imported: there
is nothing above `fn main` because there is nothing a wolf file needs
above `fn main`.

**Exercise 1-1** *(fingers · lupin)* — Type the hello program exactly as
printed and run it. Then make it print a second line of your choosing.

**Exercise 1-3** *(fingers · lupin)* — Braces interpolate expressions,
not only names. Print a sentence that computes `6 * 7` twice inside one

## 1.2 Installing the one tool

Wolf ships as one binary. `wolf` builds, runs, tests, benchmarks,
formats, and serves your editor; there is no separate package manager,
no build-system layer, no second executable to keep in step with the
first. That is a design decision with teeth, and the book leans on it
everywhere.

It is also not true yet, and this book does not pretend otherwise. Today
the toolchain is two programs:

- **`wolf`** — the compiler. It reads your program and checks it. It
  cannot yet produce an executable.
- **`lupin`** — the reference interpreter. It runs your program.

Ask the tools who they are and they tell you:

```console
$ wolf --version
wolf 0.0.1 (wolfgang)
$ lupin --version
lupin 0.1.1 (wolf-interp, pin cbde620)
```

Ask `wolf` to build something and it declines, with the address of the
work:

```console
$ wolf
wolf: pre-alpha scaffold; `wolf build|run` lands at sprint s31
```

Two tools for now, then; one when that line comes true. Every page in
this book says which of them is speaking, and the promise stands as a
promise: the book will never ask you to install a second toolchain to
follow it. The colophon records the exact versions each printing is true
for, and your own `--version` lines are how you check that they are
yours.

Both are cargo projects, so both build the same way on every tier-1
platform (linux x86-64 and aarch64, macOS aarch64, windows x86-64).
Given a Rust toolchain and the two repositories, the commands are the
ones this book's own CI runs:

```console
$ (cd wolf-lang && cargo build --bin wolf)
$ (cd wolf-interp && cargo build --release --bin lupin)
```

Cargo prints its usual progress and leaves `wolf` under
`wolf-lang/target/debug/` and `lupin` under
`wolf-interp/target/release/`. Put both on your `PATH`, run the two
`--version` commands above, and the rest of the chapter works.

### Why there are two

The second tool is not a stopgap that got a name. `lupin` is an
independent implementation of the wolf specification, written from the
spec rather than from the compiler's source, and its day job is to
disagree with the compiler: a program whose behavior differs between the
two is a bug in one of them or a hole in the spec, and it gets found
before you meet it. A language with one implementation cannot tell the
difference between what it specified and what it happens to do.

For you, today, the useful consequence is that wolf programs run. The
compiler checks them; the interpreter runs them; both cite the same
specification clauses when they refuse, and you will watch them agree in
§1.5.

## 1.3 Scripts before projects

A wolf program can be one file, run in place:

```console
$ lupin hello.lu
hello, wolf
```

There is no project to create first, no manifest to write, no directory
layout to honor, no virtual environment to activate, no lockfile to
drift out of date. The file is the program. Chapter 22 covers what
happens when one file stops being enough, and that is a later problem
than most languages make it.

> **Coming from Python:** the equivalent Python is about as short —
>
> ```python
> print("hello, wolf")
> ```
>
> — and the difference is not in the file, it is around it. As soon as
> the script needs a library, Python asks for a virtual environment, a
> `requirements.txt` or a `pyproject.toml`, and a promise from you that
> the environment on the next machine matches this one. Wolf's answer is
> that a script declares its own dependencies in its own head, so the
> file remains the whole truth. That machinery is not in the toolchain
> yet, and this book prints no sample it cannot run; when it lands, this
> section grows the four lines it takes.

The value `main` returns is the process exit code:

```console
$ lupin hello.lu
hello, wolf
$ echo $?
0
```

That is the last expression of `main`, handed to the shell. Wolf has no
`return` ceremony at the end of a function — the last expression of a
block is its value, which is a rule you will meet again in every `if`
and `match` you write.

Loops come in the two shapes you expect. `for x in xs` walks a sequence;
`while cond` repeats until the condition fails. Both are in §1.1's
program, and the exercises below are where you write one.

## 1.4 The REPL: a spec you can interrogate

Run `lupin` with no arguments and it opens a session. Expressions
evaluate and print their value and their type; declarations persist for
as long as the session lives.

```wolf-repl
wolf> 6 * 7
42 : i32
wolf> "wolf".len
4 : i64
wolf> :type "wolf".len
i64
wolf> let howl = "awoo"
wolf> "{howl} {howl}"
awoo awoo : str
wolf> fn double(n: int) -> int { n * 2 }
defined fn `double`
wolf> double(21)
42 : i64
wolf> :quit
```

Two things in that session are worth more than they look. The type is
printed on every line, so a question about types is one keystroke and
never a guess: `6 * 7` is `i32` because that is what an integer literal
infers to, while `"wolf".len` is `i64` because a length is. And `:type`
answers without running the program for effect, which makes the prompt a
way to interrogate the language rather than a calculator that happens to
speak it.

Because this is the reference interpreter, the answers are the
specification's answers. When a later chapter claims wolf does
something, you can ask.

A fault does not end the session:

```wolf-repl
wolf> let s = "wolf"
wolf> s[2..9]
trap(bounds): byte range 2..9 is outside a 4-byte string [mem.ub.defined] at 0..7
the session survives the trap; the world is as the fault left it [repl.trap.alive]
wolf> s.len
4 : i64
wolf> :quit
```

The prompt comes back, the world is whatever the fault left behind, and
`s` is still four bytes long. Chapter 2 is where that message stops
being a surprise.

One directive to note and not use yet: `:mem` prints the state of the
memory model — what exists, what owns it, what is still open. Part 2 is
where it becomes the most useful four characters in the tool. `:help`
lists the rest.

**Exercise 1-4** *(fingers · lupin REPL)* — Open the REPL. Compute the
number of seconds in a day, ask `:type` what type that expression has,
then define a function mid-session and call it twice. Before you ask
`:type`, write down your guess.

## 1.5 What `run` was doing for you

`lupin receipt.lu` looks like one action. It is six: the file is
tokenized, parsed, its names resolved, its types checked, its memory
discipline checked, and then — only then — run. Nothing is written to
disk. Having no artifact is what makes a script convenient; producing one
is what a compiler is for, and this section is named after the day wolf
does both.

The phases matter because they divide the ways a program can end. There
are three verdicts, and they have distinct exit codes.

**The program never starts (exit 2).** Delete a closing brace and the
file is not a wolf program at all:

```wolf,fail(E0202)
fn main() -> !int {
    print("almost")
    0
```

```console
$ lupin almost.lu
almost.lu: E0202: the file ends where `}` was required [gram.expr.block] at 45..45
$ echo $?
2
```

The compiler refuses the same file, and takes more room to do it:

```diagnostic,from(ch01/ex1-6)
error[E0202]: this `{` is never closed
 --> ./ex1-6.lu:4:19
  |
4 | fn main() -> !int {
  |                   ^ opened here
...
7 |
  | - the parser expected the closing `}` by here
  |
```

Two implementations, one rule, one error code, two voices: the
interpreter reports the byte offset where the file ran out, the compiler
points at the opener because that is where your hands go. Neither is
paraphrasing the other. `wolf --explain E0202` prints the rule behind
both.

**The program runs and hits a rule (exit 3).** §1.1's scan trusted every
row to hold a comma. Here is the row that does not, and the loop alone:

```wolf,run(exit=trap(bounds))
fn main() -> !int {
    let row = "tip 100"
    var i = 0
    while row[i..i + 1] != "," { i += 1 }
    print(row[..i])
    0
}
```

```console
$ lupin scan.lu
scan.lu: trap(bounds): byte range 7..8 is outside a 7-byte string [mem.ub.defined] at 68..81
$ echo $?
3
```

This program was legal. It started, it ran, and it walked off the end of
a seven-byte string, which wolf defines as a fault rather than leaving
it to luck: the run stops, names the operation, the range, the length,
and the clause it enforces. Chapter 3 gives faults like this one their
own section, and chapter 6 is where the receipt learns to say "this row
has no comma" instead.

**The implementation has not got there yet (exit 4).** A young toolchain
also declines work it will do later, and says so in those terms rather
than guessing:

```console
$ lupin split.lu
split.lu: unsupported: `str` has no method `split` in this machine's std subset
```

That is not a program error and it is not your mistake; it is the
implementation's edge, and you will see it a few times in chapter 2,
where the book says so in place rather than teaching around it.

What is missing from this section is `wolf build`. There is no compiled
artifact today, no `--release`, no binary to hand somebody. When the
compiler's driver lands, running a program becomes the same command
without the interpreter, and this section gains the artifact it is
named for; the colophon will tell you whether your toolchain is the one
that has it. Nothing else in this book changes.

**Exercise 1-6** *(spelunking · lupin)* — Delete the closing brace of a
working program's `main` and run it. Read the whole diagnostic: the
code, the message, the clause tag, the span. Then run `echo $?`. Which
of this section's exit codes is this, and why is it not the code a trap
would produce?
