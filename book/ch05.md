# 5. Collections and generics without fear

Chapter 3 gave the receipt a category per row. The question a category
invites is what each one comes to, and that needs somewhere to keep a
running total per name — one of the two containers this chapter is
about, plus a list to remember the order the categories arrived in:

```wolf,part(bycategory)
fn kind(name: str) -> str {
    match name {
        "tip" => "gratuity",
        "espresso" => "drink",
        _ => "food",
    }
}
fn seen_at(xs: List[str], s: str) -> int {
    var i = 0
    while i < xs.len {
        if xs[i] == s { return i }
        i += 1
    }
    0 - 1
}
```

`kind` is chapter 3's, unchanged. `seen_at` answers "have I seen this
category, and where" with the linear scan §5.1 will have a word about.
The rest is the program:

```wolf,part(bycategory, cont),run(exit=0)
fn main() -> !int {
    let rows = """
        espresso,340
        pastry,275
        tip,100
        """
    var order = List[str]()
    var totals = Map[str, int]()
    for row in rows.lines() {
        var i = 0
        while row[i..i + 1] != "," { i += 1 }
        let k = kind(row[..i])
        let cents = row[i + 1..].to_int() else 0
        if seen_at(order, k) < 0 {
            (mut order).push(k)
            totals[k] = cents
        } else {
            totals[k] += cents
        }
    }
    for k in order {
        print("{k:<10}{totals[k]:>5}")
    }
    0
}
```

```console
$ lupin totals.lu
drink       340
food        275
gratuity    100
```

Two containers, one job each: the `Map` answers "how much for this
category", the `List` answers "in what order did the categories show
up". Neither answers the other's question well, which is the honest
version of choosing a data structure.

## 5.1 `List`, `Map`, `Set`, tuples

A `List[T]` holds a sequence of `T` and grows at the end:

```wolf,run(exit=0)
fn main() -> !int {
    var cents = List[int]()
    (mut cents).push(340)
    (mut cents).push(275)
    (mut cents).push(100)
    let last = (mut cents).pop()
    print("{cents.len} left, popped {last}, first {cents[0]}, empty {cents.is_empty()}")
    0
}
```

```console
$ lupin list.lu
2 left, popped 100, first 340, empty false
```

`List[int]()` builds an empty one — the type in brackets, then the call.
`push` appends, `pop` removes and returns the last element, `len` is the
count, `is_empty` is the readable spelling of `len == 0`, and `xs[i]`
reads the element at index `i`, counting from zero. `push` and `pop`
both change the list they are called on, so every call arrives
write-marked — `(mut cents).push(340)` is §3.1's "this call writes
`cents`", in its natural habitat now — while `len`, `is_empty`, and
`xs[i]` only read, and say nothing. Push and pop at one end also make a
`List` the stack you reach for when a problem wants one.

A `Map[K, V]` associates keys with values:

```wolf,run(exit=0)
fn main() -> !int {
    var totals = Map[str, int]()
    totals["drink"] = 340
    totals["food"] = 275
    totals["drink"] += 100
    print("{totals.len} keys, drink {totals["drink"]}")
    for (k, n) in totals.pairs() {
        print("{k:<8}{n:>5}")
    }
    0
}
```

```console
$ lupin map.lu
2 keys, drink 440
drink     440
food      275
```

`m[k] = v` puts a value in, `m[k]` reads it back, `m[k] += v` updates it
in place, and `pairs()` walks the whole thing as key–value pairs, which
the `for` destructures into two names. The same square brackets that
carry the type at construction carry the key at use, which is a
deliberate economy and §5.3's subject.

A tuple is a fixed group of values of possibly different types, written
in parentheses and read by position:

```wolf,run(exit=0)
fn split_at(row: str, i: int) -> (str, int) {
    (row[..i], row[i + 1..].to_int() else 0)
}
fn main() -> !int {
    let pair = split_at("espresso,340", 8)
    print("{pair.0} costs {pair.1}")
    let (name, cents) = split_at("tip,100", 3)
    print("{name} costs {cents}")
    0
}
```

```console
$ lupin tuple.lu
espresso costs 340
tip costs 100
```

`pair.0` and `pair.1` are the elements; `let (name, cents) = …` takes
them apart in one line. A tuple is how a function returns two things
without either a struct nobody else will use or an output parameter, and
`(str, int)` in the signature says exactly what comes back.

All three fit at the prompt, where the types are on the page:

```wolf-repl
wolf> var cents = List[int]()
wolf> (mut cents).push(340)
wolf> (mut cents).push(275)
wolf> cents.len
2 : i64
wolf> cents[0]
340 : i32
wolf> let pair = ("tip", 100)
wolf> pair.1
100 : i32
wolf> var totals = Map[str, int]()
wolf> totals["drink"] = 340
wolf> totals["drink"]
340 : i32
wolf> totals.len
1 : i64
```

A length is an `i64` and an element is whatever the container holds, so
`cents.len` and `cents[0]` print different types on adjacent lines — the
distinction chapter 1 met with `"wolf".len`, holding at every container
in the language.

That leaves `Set`, and here the book has to be honest: the pinned
interpreter has not got one.

```wolf,run(exit=4)
fn main() -> !int {
    var kinds = Set[str]()
    kinds.add("drink")
    print("{kinds.len}")
    0
}
```

```console
$ lupin set.lu
set.lu: unsupported: `str` does not resolve
$ echo $?
4
```

Exit 4 is the interpreter declining the program rather than running it,
and the message blames the element type rather than the missing
container. Where a set is the
right structure in Part 1, the samples use a `List` and a linear scan,
which is what `seen_at` is doing in the program at the head of this
chapter. For the sizes in this book that costs nothing you can measure;
for a set with ten thousand members it is the wrong answer, and a hashed
set is the right one.

## 5.2 The combinator style

Here is what the top category ought to look like. It is the spelling the
language is designed for, from the program that started wolf's syntax
argument:

```wolf,run(exit=4)
fn main() -> !int {
    var totals = Map[str, int]()
    totals["drink"] = 440
    totals["food"] = 275
    for (k, n) in totals.pairs().sorted_by(fn(a, b) b.1 <=> a.1).take(1) {
        print("{k} {n}")
    }
    0
}
```

Read it left to right: take the pairs, sort them by the second element
descending, keep the first. Every step names a *result* and none of them
names a loop; `<=>` compares two values and answers −1, 0, or 1, which
is all `sorted_by` needs from you.

Now run it:

```console
$ lupin chain.lu
chain.lu: unsupported: `List` has no method `sorted_by` in this machine's std subset
$ echo $?
4
```

None of the combinators exist yet — not `sorted_by`, not `take`, not
`map`, `filter`, or `sum`. What does exist is the thing they are all
built from: an *iterator*, a value that yields elements one at a time,
which is what `lines()`, `words()`, and `pairs()` return and what `for`
consumes. `count()` is the one combinator in the subset, and chapter 2
used it.

So the section's promise arrives in the honest order. Instead of writing
the chain and then desugaring it for understanding, we write the
desugaring because it runs, and keep the chain on the page as the thing
it is a translation of:

```wolf,part(top2)
fn seen_at(xs: List[str], s: str) -> int {
    var i = 0
    while i < xs.len {
        if xs[i] == s { return i }
        i += 1
    }
    0 - 1
}
fn totals_of(order: List[str]) -> Map[str, int] {
    var totals = Map[str, int]()
    totals["drink"] = 440
    totals["food"] = 275
    totals["gratuity"] = 100
    totals
}
```

Three categories with their totals, standing in for the receipt's, and
the ranking itself:

```wolf,part(top2, cont),run(exit=0)
fn main() -> !int {
    var order = List[str]()
    (mut order).push("drink")
    (mut order).push("food")
    (mut order).push("gratuity")
    let totals = totals_of(order)
    var taken = List[str]()
    while taken.len < 2 {
        var best = ""
        for k in order {
            if seen_at(taken, k) < 0 {
                if best == "" || totals[k] > totals[best] { best = k }
            }
        }
        print("{best:<10}{totals[best]:>5}")
        (mut taken).push(best)
    }
    0
}
```

```console
$ lupin top2.lu
drink       440
food        275
```

Fifteen lines against one, and they are not the same program: the loop
version never sorts. It walks the categories twice looking for the
largest not yet printed, which for a top-2 is strictly less work than
ordering everything — and for a top-500 is strictly more. That is the
trade the combinator style makes on purpose. The chain states the shape
of the result and lets the library pick the work; the loop states the
work and leaves the reader to infer the shape. When both spell the same
answer, prefer the one that says what you meant, and reach for the loop
when the work is the thing you are choosing.

## 5.3 Generics in square brackets

`seen_at` searches a `List[str]`. The same three lines search a list of
anything, and saying so takes one pair of brackets:

```wolf,run(exit=0)
fn best[T](xs: List[T], better: fn(T, T) -> bool) -> T {
    var b = xs[0]
    var i = 1
    while i < xs.len {
        if better(xs[i], b) { b = xs[i] }
        i += 1
    }
    b
}
fn main() -> !int {
    var cents = List[int]()
    (mut cents).push(340)
    (mut cents).push(275)
    (mut cents).push(100)
    var names = List[str]()
    (mut names).push("espresso")
    (mut names).push("pastry")
    (mut names).push("tip")
    print("{best(cents, fn(a, b) a > b)} {best[str](names, fn(a, b) a < b)}")
    0
}
```

```console
$ lupin best.lu
340 espresso
```

`[T]` after the name declares a *type parameter*: `best` works for any
`T`, given a function that says which of two `T`s wins. The two calls
show both spellings — `best(cents, …)` lets the arguments determine `T`,
`best[str](names, …)` names it — and naming it is documentation rather
than a requirement, because the arguments already pin it down.

The interesting part is what `best` may do with a `T`. It compares them
by calling the function you supplied, and it does not compare them with
`>` itself, because it cannot: nothing is known about `T` at the
definition. Try it anyway and the error arrives where the mistake is:

```wolf,fail(E0501)
fn total[T](xs: List[T]) -> int {
    xs[0] + 1
}
fn main() -> !int {
    let xs = List[int]()
    print("{total(xs)}")
    0
}
```

```diagnostic,from(book/ch05/s7)
error[E0501]: the bounds on `T` say nothing about `+`
 --> ./s7.lu:5:5
  |
5 |     xs[0] + 1
  |     ^^^^^ `T` could be any type here
  |
  = note: bounds grant trait members only, and no trait covers this operator yet (operator traits
    are a later sprint); take a concrete type here, or dispatch through a trait method.
```

Read the span. The error is on line 5 of `total`, in the file where
`total` is written — not at the call, and not in a wall of text about
`List[int]`. The definition promised to work for any `T` and then used a
`T` in a way only some types allow, so the definition is wrong, and it is
wrong whether or not anybody ever calls it with an `int`. That is the
pitch: your mistakes are caught where you made them. A generic function
in a library you publish is checked once, by you, rather than
rediscovered by everyone who instantiates it.

> **Why `[]` and no turbofish.** `Map[str, int]` and `totals["drink"]`
> use the same brackets, and so do `best[str](names, …)` and `xs[i]`.
> Rust writes `HashMap<String, i32>` and then, when an expression is
> ambiguous, `parse::<i32>()` — the turbofish, which exists because `<`
> is also less-than and the parser cannot tell a generic argument from a
> comparison without help. Wolf's grammar has no such ambiguity to
> resolve, because `e[…]` parses as one postfix form and the question of
> index-versus-type-argument is settled later, by the part of the
> compiler that knows what `e` is. The cost is real and somebody pays
> it: it is paid once, in the compiler's grammar–semantics seam, instead
> of forever, in user code. The bet is that the seam's diagnostics stay
> good enough that the reader never learns it exists, and this book will
> hold the compiler to that bet.

When this chapter was first true, there were no traits — the
`fn(T, T) -> bool` parameter stood in for a comparison trait that had
not landed, and the error above said as much in its own note. The trait
system has landed since; §5.5 pays that debt. The function parameter
stays, because it is still the right teaching order: what `best` may do
with a `T` is exactly what you hand it the means to do.

## 5.4 Indexing that traps

Chapter 2's slices were checked. So is every index in this chapter:

```wolf,run(exit=trap(bounds))
fn main() -> !int {
    var cents = List[int]()
    (mut cents).push(340)
    print("{cents[0]}")
    print("{cents[1]}")
    0
}
```

```console
$ lupin index.lu
340
index.lu: trap(bounds): index 1 is outside a collection of 1 element(s) [mem.ub.defined] at 110..118
$ echo $?
3
```

One element, indexes 0 and 1 attempted, and the second one ends the
program: same trap kind and same clause as a string slice off the end,
because it is the same rule about the same kind of mistake. There is no
index that returns a garbage element and no negative index that counts
from the back — `cents[0 - 1]` traps too, reporting `index -1`.

`pop` is bounds-checked for the same reason:

```wolf,run(exit=trap(bounds))
fn main() -> !int {
    var cents = List[int]()
    let v = (mut cents).pop()
    print("{v}")
    0
}
```

```console
$ lupin pop.lu
pop.lu: trap(bounds): `pop` on an empty List [mem.ub.defined] at 60..77
$ echo $?
3
```

A stack that hands you something when it is empty is a stack that turns
one bug into two, twenty lines apart. Ask `is_empty` first — or, when a
caller can do something better with the news than dying, hand the
emptiness back as a value, which is chapter 6.

One index in the language is not checked, and it is a `Map` key:

```wolf,run(exit=0)
fn main() -> !int {
    var totals = Map[str, int]()
    totals["drink"] = 340
    print("[{totals["tip"]}]")
    0
}
```

```console
$ lupin absent.lu
[()]
```

`()` is what a lookup yields for a key that is not there — not a trap,
not a zero, and not a refusal. It is also nearly unusable: put it in
arithmetic and the run stops.

```wolf,run(exit=4)
fn main() -> !int {
    var totals = Map[str, int]()
    totals["drink"] = 340
    totals["tip"] += 100
    print("{totals["tip"]}")
    0
}
```

```console
$ lupin bump.lu
bump.lu: unsupported: `totals["tip"]` does not denote a place at run time
$ echo $?
4
```

So a `Map` in Part 1 is written the way the program at the head of this
chapter writes it: decide whether the key is new, then insert or update
deliberately. Two branches where one lookup would do is the price of
being explicit about absence, and being explicit about absence is the
habit the rest of the book rewards — a missing key is an answer, and an
answer belongs in the type system rather than in a convention about
zero.

> **What the machine does.** A `List` is a pointer, a length, and a
> capacity: `push` writes at the end and doubles the buffer when it runs
> out, which makes the cost of *n* pushes proportional to *n* even
> though individual pushes occasionally copy. `xs[i]` is an address
> computation and a comparison — the bounds check is the comparison, and
> the same analysis that hoists arithmetic checks out of loops hoists
> these when the range is provable. What none of these operations do is
> copy the elements: `pairs()` hands out views, `pop` hands the element
> over the way §4.4's returns do. Which is why `seen_at`'s linear scan
> costs one comparison per element and nothing else, and why the honest
> objection to it is the number of comparisons, not the copying.

## 5.5 Traits: the system lands

Section 5.3 promised a comparison trait "that lands with the trait
system," and for several printings that sentence was a schedule. It is
now a fact. A trait names a capability; an `impl` says a type has it;
and the compiler checks the claim where the impl is written, not where
it is used — the same definition-site honesty §5.3 taught for generics.

```wolf,run(exit=0, stdout="wolf howls")
trait Speak {
    fn cry(self) -> str
}
struct Wolf { name: str }
impl Speak for Wolf {
    fn cry(self) -> str { "{self.name} howls" }
}
fn main() -> !int {
    let w = Wolf { name: "wolf" }
    print(w.cry())
    0
}
```

A trait may also carry a body of its own — a *default* — and the
default may call the methods the trait declares. Dispatch goes through
the implementing type: the default's `self.name()` below finds `Pack`'s
`name`, not some abstract one.

```wolf,run(exit=0, stdout="hi wolf")
trait Greeter {
    fn name(self) -> str
    fn greet(self) -> str { "hi {self.name()}" }
}
struct Pack { title: str }
impl Greeter for Pack {
    fn name(self) -> str { self.title }
}
fn main() -> !int {
    let p = Pack { title: "wolf" }
    print(p.greet())
    0
}
```

Impls are not reserved for your own structs. A primitive can carry one,
and the call spells the trait's name — `Text.text(n)`, the *qualified*
form. The method sugar `n.text()` does not reach primitives yet; the
compiler refuses it by name, and this book teaches the spelling that
works today rather than the one scheduled to.

```wolf,wolf-run(exit=0, stdout="int(7)")
trait Text {
    fn text(self) -> str
}
impl Text for int {
    fn text(self) -> str { "int({self})" }
}
fn main() -> !int {
    let n: int = 7
    print(Text.text(n))
    0
}
```

All of this is resolved at compile time: the compiler knows the
concrete type at every call above and wires the call straight to the
impl. The other mode — deciding *at run time* — exists too, and wolf
spells it the way it spells every deliberate cost, out loud: `dyn`.
A `dyn Speak` is a pair of pointers, one to the value and one to a
table of its trait's methods, and a function that takes one serves
every implementing type through the same two loads:

```wolf,run(exit=0)
trait Draw {
    fn draw(self) -> str
}
struct Dot { x: int }
struct Ring { r: int }
impl Draw for Dot {
    fn draw(self) -> str { "dot at {self.x}" }
}
impl Draw for Ring {
    fn draw(self) -> str { "ring of {self.r}" }
}
fn render(o: dyn Draw) -> str { o.draw() }
fn main() -> !int {
    let d = Dot { x: 3 }
    let r = Ring { r: 9 }
    print(render(d as dyn Draw))
    print(render(r as dyn Draw))
    0
}
```

Look at what feeds `render`: a *binding*, cast with `as dyn Draw`. That
is a rule, not a style. The pair's data half points at the operand, so
the operand must be somewhere — a binding, a field, an index. Hand the
cast a temporary and the compiler explains the rule better than this
paragraph does:

```wolf,fail(E0810)
trait Draw {
    fn draw(self) -> str
}
struct Dot { x: int }
impl Draw for Dot {
    fn draw(self) -> str { "dot at {self.x}" }
}
fn render(o: dyn Draw) -> str { o.draw() }
fn main() -> !int {
    print(render(Dot { x: 3 } as dyn Draw))
    0
}
```

`a temporary has no home — bind it first.` The fix is the one the note
spells: `let home = Dot { x: 3 }`, then `home as dyn Draw`. A `dyn`
crosses a call today; carrying one inside a container is the compiler
being honest about its schedule again, and the refusal names itself.

One boundary, stated so no reader over-reaches: `==` and `<=>` do not
dispatch through `Eq` or `Ord` at this printing. The design that
bridges them is decided; the code that does it has not landed. Until it
does, comparison traits are called the way every trait here is called —
by name.
