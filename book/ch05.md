# 5. Collections and generics

Chapter 3 gave the receipt a category per row. The question a category
invites is what each one comes to, and that needs somewhere to keep a
running total per name, which is one of the two containers this
chapter is about:

```wolf,part(bycategory)
fn kind(name: str) -> str {
    match name {
        "tip" => "gratuity",
        "espresso" => "drink",
        _ => "food",
    }
}
```

`kind` is chapter 3's, unchanged. The rest is the program, and it runs
under `wolf`:

```wolf,part(bycategory, cont),wolf-run(exit=0)
fn main() -> !int {
    let rows = """
        espresso,340
        pastry,275
        tip,100
        """
    var totals = Map[str, int]()
    for row in rows.lines() {
        var i = 0
        while row[i..i + 1] != "," { i += 1 }
        let k = kind(row[..i])
        let cents = row[i + 1..].to_int() else 0
        totals[k] = (totals[k] else 0) + cents
    }
    for (k, n) in totals.pairs() {
        print("{k:<10}{n:>5}")
    }
    0
}
```

```console
$ wolf run totals.lu
drink       340
food        275
gratuity    100
```

One container, and one line of counting. `totals[k]` asks the `Map`
for a category's running total and answers `none` when there is no
entry for `k` yet; `else 0` reads that answer as zero, the way
`to_int() else 0` reads a field with no number in it; `+ cents` adds
the row; and `totals[k] = …` writes the sum back, inserting the entry
on a category's first row and replacing it on every row after. The
`Map` answers "how much for this category". What it does not promise
is the order the categories showed up in: `pairs()` walks the entries
in an order the language leaves unspecified, and §5.2, whose query
needs that order, keeps it in a `List`.

## 5.1 `List`, `Map`, `Set`, tuples

A `List[T]` holds a sequence of `T` and grows at the end:

```wolf,run(exit=0)
fn main() -> !int {
    var cents = List[int]()
    (mut cents).push(340)
    (mut cents).push(275)
    (mut cents).push(100)
    let last = (mut cents).pop()
    print("{cents.len} left, popped {last}, first {cents[0]}, empty {cents.is_empty()}")
    0
}
```

```console
$ lupin list.lu
2 left, popped 100, first 340, empty false
```

`List[int]()` builds an empty one: the type in brackets, then the call.
`push` appends, `pop` removes and returns the last element, `len` is the
count, `is_empty` is the readable spelling of `len == 0`, and `xs[i]`
reads the element at index `i`, counting from zero. `push` and `pop`
both change the list they are called on, so every call arrives
write-marked (`(mut cents).push(340)` is §3.1's "this call writes
`cents`", in its natural habitat now), while `len`, `is_empty`, and
`xs[i]` only read, and say nothing. Push and pop at one end also make a
`List` the stack you reach for when a problem wants one.

A `Map[K, V]` associates keys with values:

```wolf,run(exit=0)
fn main() -> !int {
    var totals = Map[str, int]()
    totals["drink"] = 340
    totals["food"] = 275
    totals["drink"] = (totals["drink"] else 0) + 100
    print("{totals.len} keys, drink {totals["drink"]}")
    for (k, n) in totals.pairs() {
        print("{k:<8}{n:>5}")
    }
    0
}
```

```console
$ lupin map.lu
2 keys, drink 440
drink     440
food      275
```

`m[k] = v` puts a value in, `m[k]` reads it back, and `pairs()` walks
the whole thing as key–value pairs, which the `for` destructures into
two names. Two sentences about the read, which the rest of the chapter
leans on. What `m[k]` answers is `int ! {none}`: the value when the key
is bound and the mark `none` when it is not, so a `Map` is never asked
to invent a number, and `else 0` is how a running total reads a key it
has not seen (§5.4 has the other half of that story). And a key is a
`str`, an `int`, a `char` or a `bool` this edition, the four types
whose equality the language itself defines, so the map can answer "is
this the same key" without being told what sameness means. The same
square brackets that carry the type at construction carry the key at
use. The economy is deliberate, and §5.3 returns to it.

A tuple is a fixed group of values of possibly different types, written
in parentheses and read by position:

```wolf,run(exit=0)
fn split_at(row: str, i: int) -> (str, int) {
    (row[..i], row[i + 1..].to_int() else 0)
}
fn main() -> !int {
    let pair = split_at("espresso,340", 8)
    print("{pair.0} costs {pair.1}")
    let (name, cents) = split_at("tip,100", 3)
    print("{name} costs {cents}")
    0
}
```

```console
$ lupin tuple.lu
espresso costs 340
tip costs 100
```

`pair.0` and `pair.1` are the elements; `let (name, cents) = …` takes
them apart in one line. A tuple is how a function returns two things
without either a struct nobody else will use or an output parameter, and
`(str, int)` in the signature says exactly what comes back.

All three fit at the prompt, where the types are on the page:

```wolf-repl
wolf> var cents = List[int]()
wolf> (mut cents).push(340)
wolf> (mut cents).push(275)
wolf> cents.len
2 : i64
wolf> cents[0]
340 : i32
wolf> let pair = ("tip", 100)
wolf> pair.1
100 : i32
wolf> var totals = Map[str, int]()
wolf> totals["drink"] = 340
wolf> totals["drink"]
340 : i32
wolf> totals.len
1 : i64
```

A length is an `i64` and an element is whatever the container holds, so
`cents.len` and `cents[0]` print different types on adjacent lines.
Chapter 1 met the same distinction with `"wolf".len`, and it holds at
every container in the language.

That leaves `Set`, and the sentence about it is short: this edition's
std has no set container. Where a set is the right structure, the
samples in Part 1 use a `List` and a linear scan, which is what
`seen_at` does in §5.2. For the
sizes in this book the scan costs nothing you can measure; for a set
with ten thousand members a hashed set is the right structure.

## 5.2 The combinator style

The program at the head of the chapter built a table. The first thing
to ask of a table is a query, and the first query worth asking of this
one is which two categories cost the most. A query has two spellings,
and this section is about telling them apart.

The first spelling says what the result *is*: the table's pairs,
ordered by amount, first two.

```text
totals.pairs().sorted_by(fn(a, b) b.1 <=> a.1).take(2)
```

Read left to right, every step names a result and none of them names a
loop. That is the combinator style, and it is the spelling the language
is designed for. This edition's std ships one combinator, `count()`,
and chapter 2 used it; a sort is not among them, so the line above is
the shape of the answer and not a program this book runs.

The second spelling says how to *make* the result, and it is not the
same program: the chain sorts all three categories, and the loop below
never sorts. It picks the largest category not yet picked, twice. Two
selections against one sort is the trade: for a top-2 of three, the
selections are less work than ordering everything, and for a top-500 of
ten thousand they are more. The loop is the spelling where the work
itself is the thing you are choosing:

```wolf,part(top2)
fn top(order: List[str], totals: Map[str, int], n: int) -> List[str] {
    var picked = List[str]()
    while picked.len < n {
        var best = ""
        for k in order {
            if seen_at(picked, k) < 0 {
                if best == "" || (totals[k] else 0) > (totals[best] else 0) { best = k }
            }
        }
        (mut picked).push(best)
    }
    picked
}
```

`top` reads all three of its parameters: `order` is the list it walks,
`totals` is what it compares, and `n` is how many times it walks. Each
pass finds the best category not already in `picked`; `seen_at` is the
linear scan §5.1 promised, `else 0` reads a total the way the head of
the chapter wrote one, and `best == ""` means "nothing picked yet on
this pass", which is safe because no category is the empty string. The
result is a new `List`, in the order the passes found things.

`kind` is the head of the chapter's. `seen_at` answers "have I seen
this string, and where", and answers `-1` for no:

```wolf,part(top2, cont)
fn kind(name: str) -> str {
    match name {
        "tip" => "gratuity",
        "espresso" => "drink",
        _ => "food",
    }
}
fn seen_at(xs: List[str], s: str) -> int {
    var i = 0
    while i < xs.len {
        if xs[i] == s { return i }
        i += 1
    }
    -1
}
```

And `main`, which is the head of the chapter's with two lines changed.
The query wants the categories in the order they arrived, which is the
one thing the `Map` does not promise, so the loop keeps that order in a
`List` beside the totals: `seen_at` asks the list whether a category is
new, and the map counts as it did before. The last loop asks the query
instead of printing the whole table. This program runs under `wolf`:

```wolf,part(top2, cont),wolf-run(exit=0)
fn main() -> !int {
    let rows = """
        espresso,340
        pastry,275
        tip,100
        """
    var order = List[str]()
    var totals = Map[str, int]()
    for row in rows.lines() {
        var i = 0
        while row[i..i + 1] != "," { i += 1 }
        let k = kind(row[..i])
        let cents = row[i + 1..].to_int() else 0
        if seen_at(order, k) < 0 { (mut order).push(k) }
        totals[k] = (totals[k] else 0) + cents
    }
    for k in top(order, totals, 2) {
        print("{k:<10}{totals[k] else 0:>5}")
    }
    0
}
```

```console
$ wolf run top2.lu
drink       340
food        275
```

The chain says what the result is; the loop says how to make it. Write
the chain when it says what you meant, and the loop when the work is
what you are choosing.

## 5.3 Generics in square brackets

`seen_at` searches a `List[str]`. The same three lines search a list of
anything, and saying so takes one pair of brackets:

```wolf,run(exit=0)
fn best[T](xs: List[T], better: fn(T, T) -> bool) -> T {
    var b = copy xs[0]
    var i = 1
    while i < xs.len {
        if better(xs[i], b) { b = copy xs[i] }
        i += 1
    }
    b
}
fn main() -> !int {
    var cents = List[int]()
    (mut cents).push(340)
    (mut cents).push(275)
    (mut cents).push(100)
    var names = List[str]()
    (mut names).push("espresso")
    (mut names).push("pastry")
    (mut names).push("tip")
    print("{best(cents, fn(a, b) a > b)} {best[str](names, fn(a, b) a < b)}")
    0
}
```

```console
$ lupin best.lu
340 espresso
```

`[T]` after the name declares a *type parameter*: `best` works for any
`T`, given a function that says which of two `T`s wins. The two calls
show both spellings (`best(cents, …)` lets the arguments determine `T`;
`best[str](names, …)` names it), and naming it is documentation,
because the arguments already pin it down.

`copy` is the second line's whole story, and it is the word chapter 3
read out of the compiler's help text. It is there because of what
`best` does not know. Indexing a `List[T]` hands the element over, and
for a `T` the definition knows nothing about the compiler assumes the
worst: the element may be a `str`, or something else that must not be
duplicated, so `var b = xs[0]` moves it out of the list, and the next
line's `xs.len` reads a value that moved away. The consequence is a
refusal at compile time, at that `xs.len`, with the same E1001 chapter
3 met; no program observes a shorter list, because no such program is
built. Two errors, one cause, and the compiler prints the same repair
under both of them. `copy` takes a second value and leaves the list
holding what it held, which is what a function that only inspects a
list should do. A concrete list needs none of this: `let c = cents[1]`
on a `List[int]` copies the word and leaves the list whole, because an
`int` copies, and §5.1's block read `cents[0]` in a hole and asked
`is_empty` of the same list in the same line. What the copy costs is
chapter 7's subject; what it means here is that `best` reads its
argument instead of consuming it. It is also the one thing `best` may
do to a `T` without being handed the means: `copy x` produces an
independent value from any type at all, granted by no bound and carried
by no trait.

The interesting part is what `best` may do with a `T`. It compares them
by calling the function you supplied, and it does not compare them with
`>` itself, because it cannot: nothing is known about `T` at the
definition. Try it anyway and the error arrives where the mistake is:

```wolf,fail(E0501)
fn total[T](xs: List[T]) -> int {
    xs[0] + 1
}
fn main() -> !int {
    let xs = List[int]()
    print("{total(xs)}")
    0
}
```

```diagnostic,from(book/ch05/s5)
error[E0501]: the bounds on `T` say nothing about `+`
 --> ./s5.lu:5:5
  |
5 |     xs[0] + 1
  |     ^^^^^ `T` could be any type here
  |
  = note: bounds grant trait members only, and no trait covers this operator yet (operator traits
    are a later sprint); take a concrete type here, or dispatch through a trait method.
```

Read the span. The error is on line 5 of `total`, in the file where
`total` is written, not at the call. The definition promised to work
for any `T` and then used a `T` in a way only some types allow, so the
definition is wrong, and it is wrong whether or not anybody ever calls
it with an `int`. A generic function in a library you publish is
checked once, by you, not rediscovered by everyone who instantiates it.

> **Why `[]` and no turbofish.** `Map[str, int]` and `totals["drink"]`
> use the same brackets, and so do `best[str](names, …)` and `xs[i]`.
> Rust writes `HashMap<String, i32>` and then, when an expression is
> ambiguous, `parse::<i32>()`, the turbofish, which exists because `<`
> is also less-than and the parser cannot tell a generic argument from a
> comparison without help. Wolf's grammar has no such ambiguity to
> resolve, because `e[…]` parses as one postfix form and the question of
> index-versus-type-argument is settled later, by the part of the
> compiler that knows what `e` is. The cost is paid once, in the
> compiler's grammar–semantics seam, instead of at every call site. The
> bet is that the seam's diagnostics stay good enough that the reader
> never learns it exists, and this book will hold the compiler to that
> bet.

The `fn(T, T) -> bool` parameter is a teaching choice; a trait could
name the comparison, and §5.5 builds exactly that kind of capability.
The function parameter stays because it keeps the rule visible: what
`best` may do with a `T` is exactly what you hand it the means to do.

## 5.4 Indexing that traps

Chapter 2's slices were checked. So is every index in this chapter:

```wolf,run(exit=trap(bounds))
fn main() -> !int {
    var cents = List[int]()
    (mut cents).push(340)
    print("{cents[0]}")
    print("{cents[1]}")
    0
}
```

```console
$ lupin index.lu
340
index.lu: trap(bounds): index 1 is outside a collection of 1 element(s) [mem.ub.defined] at 5:13
$ echo $?
3
```

One element, indexes 0 and 1 attempted, and the second one ends the
program: same trap kind and same clause as a string slice off the end,
because it is the same rule about the same kind of mistake. There is no
index that returns a garbage element and no negative index that counts
from the back: `cents[-1]` traps too, reporting `index -1`.

`pop` is the other shape. An empty list is not a mistake to fault on,
it is a question with an answer, so `pop` hands back `int ! {none}` and
the answer is `none`:

```wolf,run(exit=0, stdout="none")
fn main() -> !int {
    var cents = List[int]()
    let v = (mut cents).pop()
    print("{v}")
    0
}
```

```console
$ lupin pop.lu
none
$ echo $?
0
```

`pop`, `get`, `first` and `last` all read this way: each answers the
element or the mark `none`, and none of the four faults on any input.
The subscript is the faulting twin — `cents[0]` on an empty list traps,
because an index the program computed and got wrong is a different
event from a lookup that came up empty. Ask `is_empty` first when the
distinction matters, and let `else` read the mark when it does not
(chapter 6's subject).

One index in the language never traps, and it is a `Map` key. This
program runs under `wolf`:

```wolf,wolf-run(exit=0, stdout="[none]")
fn main() -> !int {
    var totals = Map[str, int]()
    totals["drink"] = 340
    print("[{totals["tip"]}]")
    0
}
```

```console
$ wolf run absent.lu
[none]
```

`none` is what a lookup answers for a key that is not there: not a
trap, not a zero, and not a refusal. It is `pop`'s answer on an empty
list, for `pop`'s reason: an index the program computed and got wrong
is a mistake, and a key that happens not to be bound is a question,
so `m[k]` is `int ! {none}` and never faults. What the mark rules out
is counting up from an absence by accident. `m[k] += v` would have to
read a value that may not exist, and the compiler refuses it where it
is written:

```wolf,fail(E0417)
fn main() -> !int {
    var totals = Map[str, int]()
    totals["drink"] += 340
    0
}
```

```diagnostic,from(book/ch05/s9)
error[E0417]: cannot update `totals["drink"]` in place: the key may be absent
 --> ./s9.lu:6:5
  |
6 |     totals["drink"] += 340
  |     ------ `totals` is a `Map`
  |     ^^^^^^^^^^^^^^^ a `Map` index is a row, not a place
  |
  = note: `m[k]` is `V ! {none}` ([mem.map.absent]): reading it asks whether the key is bound, and
    an absent key has no value to update. `m[k] = v` alone inserts or replaces.
  = note: spell the two halves — `totals["drink"] = (totals["drink"] else 0) + …` — or count with
    std's named operation, `map.tally(mut totals, k)` (`use std.map`), which is that
    statement for an `int`-valued map.
```

The first note is the rule and the second is the spelling this chapter
has used from its first program: read with a default, then write the
sum. `m[k] = v` on its own is legal on any key, inserting when the key
is absent and replacing when it is bound, which is why the write half
never needs a branch. One line where a lookup and a guess would do is
the price of being explicit about absence, and a missing key is an
answer with a type.

> **What the machine does.** A `List` is a pointer, a length, and a
> capacity: `push` writes at the end and doubles the buffer when it runs
> out, which makes the cost of *n* pushes proportional to *n* even
> though individual pushes occasionally copy. `xs[i]` is an address
> computation and a comparison: the bounds check is the comparison, and
> the same analysis that hoists arithmetic checks out of loops hoists
> these when the range is provable. None of these operations copies the
> elements: `pairs()` hands out views, `pop` hands the element over the
> way §4.4's returns do. Which is why `seen_at`'s linear scan costs one
> comparison per element and nothing else, and why the objection to it
> is the number of comparisons, not the copying.

## 5.5 Traits

A trait names a capability; an `impl` says a type has it; and the
compiler checks the claim where the impl is written, not where it is
used: the same definition-site honesty §5.3 taught for generics.

```wolf,run(exit=0, stdout="wolf howls")
trait Speak {
    fn cry(self) -> str
}
struct Wolf { name: str }
impl Speak for Wolf {
    fn cry(self) -> str { "{self.name} howls" }
}
fn main() -> !int {
    let w = Wolf { name: "wolf" }
    print(w.cry())
    0
}
```

A trait may also carry a body of its own (a *default*), and the
default may call the methods the trait declares. Dispatch goes through
the implementing type: the default's `self.name()` below finds `Pack`'s
`name`, not some abstract one.

```wolf,run(exit=0, stdout="hi wolf")
trait Greeter {
    fn name(self) -> str
    fn greet(self) -> str { "hi {self.name()}" }
}
struct Pack { title: str }
impl Greeter for Pack {
    fn name(self) -> str { self.title }
}
fn main() -> !int {
    let p = Pack { title: "wolf" }
    print(p.greet())
    0
}
```

Impls are not reserved for your own structs. A primitive can carry one,
and on a primitive the call spells the trait's name: `Text.text(n)`,
the *qualified* form. The method sugar `n.text()` does not reach a
primitive receiver; the compiler refuses it by name.

All of this is resolved at compile time: the compiler knows the
concrete type at every call above and wires the call straight to the
impl. The other mode, deciding *at run time*, exists too, and wolf
spells it the way it spells every deliberate cost, out loud: `dyn`.
A `dyn Speak` is a pair of pointers, one to the value and one to a
table of its trait's methods, and a function that takes one serves
every implementing type through the same two loads:

```wolf,run(exit=0)
trait Draw {
    fn draw(self) -> str
}
struct Dot { x: int }
struct Ring { r: int }
impl Draw for Dot {
    fn draw(self) -> str { "dot at {self.x}" }
}
impl Draw for Ring {
    fn draw(self) -> str { "ring of {self.r}" }
}
fn render(o: dyn Draw) -> str { o.draw() }
fn main() -> !int {
    let d = Dot { x: 3 }
    let r = Ring { r: 9 }
    print(render(d as dyn Draw))
    print(render(r as dyn Draw))
    0
}
```

Look at what feeds `render`: a *binding*, cast with `as dyn Draw`. That
is a rule, not a style. The pair's data half points at the operand, so
the operand must be somewhere (a binding, a field, an index). Hand the
cast a temporary and the compiler explains the rule better than this
paragraph does:

```wolf,fail(E0810)
trait Draw {
    fn draw(self) -> str
}
struct Dot { x: int }
impl Draw for Dot {
    fn draw(self) -> str { "dot at {self.x}" }
}
fn render(o: dyn Draw) -> str { o.draw() }
fn main() -> !int {
    print(render(Dot { x: 3 } as dyn Draw))
    0
}
```

`a temporary has no home — bind it first.` The fix is the one the note
spells: `let home = Dot { x: 3 }`, then `home as dyn Draw`.

One boundary, stated so no reader over-reaches: `==` and `<=>` do not
dispatch through `Eq` or `Ord`. A comparison trait is called the way
every trait in this chapter is called, by name.
