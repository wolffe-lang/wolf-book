# 3. Values and expressions

Chapter 2 was about one type. This chapter is about the language around
it: what a name holds, what a piece of code hands back, and what
arithmetic does when the answer will not fit.

The receipt has been printing what it read. Now it has an opinion about
it:

```wolf,part(categories)
fn kind(name: str) -> str {
    match name {
        "tip" => "gratuity",
        "espresso" => "drink",
        _ => "food",
    }
}
```

```wolf,part(categories, cont),run(exit=0)
fn main() -> !int {
    let rows = """
        espresso,340
        pastry,275
        tip,100
        """
    var total = 0
    for row in rows.lines() {
        var i = 0
        while row[i..i + 1] != "," { i += 1 }
        let name = row[..i]
        let cents = row[i + 1..].to_int() else 0
        let mark = if cents > 300 { "*" } else { " " }
        total += cents
        print("{mark}{name:<10}{kind(name):<9}{cents:>5}")
    }
    print(" {"total":<19}{total:>5}")
    0
}
```

```console
$ lupin categories.lu
*espresso  drink      340
 pastry    food       275
 tip       gratuity   100
 total                715
```

Look at what `kind` does not contain: a `return`. Its whole body is one
`match`, and the value of that `match` is the value of the call. `mark`
is the value of an `if`. Neither is a special form; both are the ordinary
way wolf spells a choice, and the two rules behind them run this whole
chapter. A name holds one value for good, or holds a series of them. Code
that looks like a statement is an expression with a value you may keep or
discard.

## 3.1 `let`, `var`, and handing values over

Both spellings appeared in chapter 1 without explanation. Here they are
side by side at the prompt:

```wolf-repl
wolf> let width = 10
wolf> width
10 : i32
wolf> var total = 0
wolf> total += 715
wolf> total
715 : i32
wolf> let frozen = total
wolf> total = 0
wolf> "{frozen} {total}"
715 0 : str
wolf> :type frozen
i32
```

`let` names a value once. `var` names a place that takes a series of
them: `total` is 0, then 715, then 0 again, and it is the same `total`
throughout: one name, one type, new contents. `frozen` is a `let`, so
it is 715 for as long as it exists, and the later `total = 0` does not
reach it.

Reach for `let` first: it is the
narrower claim, and the compiler holds you to it:

```wolf,fail(E0410)
fn main() -> !int {
    let width = 10
    width = 12
    print("{width}")
    0
}
```

```diagnostic,from(book/ch03/s1)
error[E0410]: `width` is bound with `let`, so it cannot be assigned again
 --> ./s1.lu:6:5
  |
5 |     let width = 10
  |     --- the binding is made immutable here
6 |     width = 12
  |     ^^^^^ this assignment needs a mutable binding
  |
  = note: `let` names a value once. Declare the binding with `var` to update it in place, or
    shadow it with a second `let` if the next value is really a new thing.
help: make the binding mutable: `var`
  |
5 |     var width = 10
  |
```

The note names both repairs, and they are different claims about your
program. `var width` says this quantity changes over time. A second
`let width` says the old value is finished and a new thing is taking its
name. Wolf lets you do either and asks you to say which.

So far every value has been a number or a string slice, two words at
most, copied wherever they go. Values get bigger than that. A `List` owns
its elements:

```wolf,run(exit=0)
fn main() -> !int {
    var names = List[str]()
    (mut names).push("ada")
    (mut names).push("grace")
    let roster = names
    print("{roster.len} names")
    0
}
```

```console
$ lupin roster.lu
2 names
```

Two spellings in that program are new, and the smaller one first.
`push` puts an element on the end of the list (lists get their own
chapter, chapter 5), and it changes the list it is called on,
which is why the call is written `(mut names).push(…)` and not
`names.push(…)`: a call that writes through a name says so at the call,
where a reader can see it without looking up what `push` does. For now,
read `(mut names)` as "this call writes `names`" and nothing more.
Chapter 7 tells why the language insists, and the whole system the
marker belongs to; until then this is the only
place the word appears: on the left of a method call that writes.

The fifth line shows the rule: assignment hands the
value over. `roster` now holds the list `names` was holding, not a
second list with the same contents and not a view onto somebody else's
list.

Which leaves a question about `names`, and wolf answers it before the
program runs:

```wolf,fail(E1001)
fn main() -> !int {
    var names = List[str]()
    let roster = names
    print("{roster.len} {names.len}")
    0
}
```

```diagnostic,from(book/ch03/s3)
error[E1001]: `names.len` is used here after its value moved away
 --> ./s3.lu:7:26
  |
6 |     let roster = names
  |                  ----- `names` moved here
7 |     print("{roster.len} {names.len}")
  |                          ^^^^^^^^^ used after the move
  |
  = note: `names.len` is part of `names`; moving one empties the other. Disjoint fields stay
    usable.
  = note: re-initializing the place (assigning to it) also makes it usable again.
help: to keep the original, copy it at the move
  |
6 |     let roster = copy names
  |
```

The interpreter enforces the same rule at the other end of the day:
the program starts, reaches the same read, and stops there:

```console
$ lupin roster.lu
roster.lu: trap(use-after-move): `names` was moved out and is uninitialized here [mem.tier0.move.2] at 4:26; `names` moved here at 3:18
$ echo $?
3
```

Two tools, one rule, the two enforcement moments chapter 1 set up: the
compiler proves it before the program starts, the interpreter catches it
in the act. Neither invents a value for `names` to have.

Take the second note literally: `names` is not poisoned, it is
empty; hand it something and it is a working name again:

```wolf,run(exit=0)
fn main() -> !int {
    var names = List[str]()
    (mut names).push("ada")
    let roster = names
    names = List[str]()
    (mut names).push("grace")
    print("{roster.len} {names.len}")
    0
}
```

```console
$ lupin reinit.lu
1 1
```

That is the whole of the story this chapter tells. The much longer one
is chapter 7's: why the rule exists, what it buys, why a language would
choose it over a garbage collector, and what the `copy` in the
compiler's suggestion costs. Chapter 7 opens on this
diagnostic and does not stop for a while. Part 1 needs only the
direction of the handover and the two verdicts above. You will write a
great deal of wolf on that much.

## 3.2 Everything is an expression

An expression is anything with a value. In wolf that includes the
constructs other languages make statements, which is why there is no
ternary operator and nothing missing where one would be:

```wolf,wolf-run(exit=0)
fn main() -> !int {
    let cents = 275
    let band = match cents / 100 {
        0 => "under a dollar",
        1..=2 => "a dollar or two",
        d if d < 10 => "{d} dollars",
        _ => "expensive",
    }
    let mark = if cents > 300 { "*" } else { "" }
    let padded = {
        let body = "{cents}"
        "{body:>6}"
    }
    print("{padded} {band}{mark}")
    0
}
```

```console
$ wolf run bands.lu
   275 a dollar or two
```

This program runs under `wolf`. Its arms are the four things an arm can
be, and any switch you have written already spells three of them. `0` is
a literal. `1..=2` is a *range*: `..=` takes its high end, `..` stops
before it, and both ends are literals — over `char` the order is scalar
order, so `'a'..='z'` is twenty-six letters and nothing else.
`d if d < 10` binds the value and then asks a question about it, and an
arm whose guard answers no falls through to the next one. `_` takes what
is left, and it is still required: nothing adds these arms up, so an
`int` still has values none of them names.

Three shapes, one rule. A `match` has the value of the arm that applied.
An `if`/`else` has the value of the branch that ran. A brace-delimited
block has the value of its last expression, which is why `padded` is a
string and why `main` ends with a bare `0` and no `return`. A block also
scopes what it declares: `body` exists inside those braces and nowhere
else, so a temporary name in a long computation costs nothing outside
it.

Because the value comes from the last expression, an `if` used for its
effect and an `if` used for its value are the same `if`. Chapter 1's
receipt wrote `if i > width { width = i }` and threw the value away.
Here it is kept. Nothing about the construct changed.

`else` may also start its own line, which is worth knowing because the
alignment that buys is sometimes the clearest thing on the page:

```wolf,run(exit=0, stdout="a<tab>b<nl>c")
fn main() -> !int {
    let s = "a\tb\nc"
    var t = ""
    var i = 0
    while i < s.len {
        if s[i..i + 1] == "\t"      { t += "<tab>" }
        else if s[i..i + 1] == "\n" { t += "<nl>" }
        else                        { t += s[i..i + 1] }
        i += 1
    }
    print(t)
    0
}
```

A line whose first token is `else` continues the statement above it, so
the chain is one construct however it is laid out. Both layouts parse;
`wolf fmt` writes them as `} else`. Appendix E is the formatter's page,
and it runs the tool on a chain shaped like this one.

The reading rule has one consequence: if a
`match` is a value, its arms have to agree what type that value is.

```wolf,fail(E0401)
fn main() -> !int {
    let n = 1
    let x = match n {
        0 => "none",
        _ => 7,
    }
    print("{x}")
    0
}
```

```diagnostic,from(book/ch03/s8)
error[E0401]: the arms of this `match` disagree about its type
 --> ./s8.lu:8:14
  |
7 |         0 => "none",
  |              ------ but this one is `str`
8 |         _ => 7,
  |              ^ this arm is `{integer}`
  |
  = note: a `match` used as a value produces one type; neither arm is more "right" — make both
    `str`, or both `{integer}`, or move the `match` into statement position.
```

"Neither arm is more right" is the compiler declining to guess. A
language that picked one would be picking for you, in a program where
one of the two arms is the typo.

Loops are the exception, and there are three of
them. `while` repeats while a condition holds. `for` walks a sequence
(including a range, written `a..b`, which yields `a` up to but not
including `b`). And `loop` repeats until something in the body says stop,
which is the one that carries a value out: `break v` makes `v` the value
of the whole loop.

```wolf,lupin-run(exit=0)
fn main() -> !int {
    let row = "espresso,340"
    var a = 0
    while row[a..a + 1] != "," { a += 1 }
    var b = 0
    for i in 0..row.len {
        if row[i..i + 1] == "," {
            b = i
            break
        }
    }
    var c = 0
    let d = loop {
        if row[c..c + 1] == "," { break c }
        c += 1
    }
    print("{a} {b} {d}")
    0
}
```

```console
$ lupin three.lu
8 8 8
```

Three spellings of chapter 2's comma scan, same answer, and the third is
the only one where the loop itself carries the answer out; the other
two needed a `var` to do it. `break` with no value leaves
the loop; `continue` skips to the next turn. When the count is known,
`for i in 0..n` says so; when the exit condition is the point, `loop`
plus `break v` says that instead.

## 3.3 Arithmetic that traps

The receipt's till is nearly full. Two more rows go in:

```wolf,lupin-run(exit=trap(overflow))
fn main() -> !int {
    var till: i32 = 2147483000
    for row in "700\n700".lines() {
        till += row.to_int() else 0
    }
    print("{till}")
    0
}
```

```console
$ lupin till.lu
till.lu: trap(overflow): `+` produced 2147483700, outside `i32` — checked arithmetic traps in every profile (X3); spell intended overflow `wrapping[i32]` [arith.checked] at 4:9
$ echo $?
3
```

Push an `i32` past its ceiling and the program does not wrap, does not
continue, and does not negotiate. That is a *trap*: the fault of a
defined execution. The program was legal, it ran, and it hit a rule wolf
enforces at runtime — in release builds too, which is the part that
surprises C programmers. The line names the operation, the true product,
the type that could not hold it, the decision it enforces, and the
spelling for the rare case where wrapping was the plan. Nothing here is
undefined; the program's last act is to tell you exactly what happened.
Most bugs should be so polite.

Division by zero is the same kind of event, and it does not matter how
the zero arrived:

```wolf,lupin-run(exit=trap(div-zero))
fn main() -> !int {
    let rows = ""
    var total = 0
    var count = 0
    for row in rows.lines() {
        total += row.to_int() else 0
        count += 1
    }
    print("mean {total / count}")
    0
}
```

```console
$ lupin mean.lu
mean.lu: trap(div-zero): division by zero is defined behavior in wolf: it traps [mem.ub.defined] at 9:18
$ echo $?
3
```

An empty input means the loop never ran, so `count` is still 0 and the
average of nothing is a trap rather than whatever the
hardware felt like. The bug is in the program (averages of empty
collections are the caller's problem), and the trap is where you find it,
with the clause it enforces attached.

When wraparound is what you want, the type says so, and then it is not a
fault at all:

```wolf,lupin-run(exit=0)
fn main() -> !int {
    var checksum: wrapping[i32] = 2147483647
    checksum += 1
    var clamped: saturating[i32] = 2147483647
    clamped += 1
    print("{checksum} {clamped}")
    0
}
```

```console
$ lupin wrap.lu
-2147483648 2147483647
```

`wrapping[i32]` wraps to the bottom of the range; `saturating[i32]`
stops at the top and stays. Both are ordinary types you can put on a
binding, a field, or a parameter, which means the decision is written
where the data is declared, not at each operation, and a reader
of `checksum += 1` can look up what that line meant. A hash function
wants `wrapping`. A gauge wants `saturating`. A receipt total wants
neither, which is why the trap above is the right answer.

> **The bill for checking.** Every arithmetic operation in wolf carries
> a test the C version does not: compute, check the flag the hardware
> already set, branch to the trap on failure. The branch is never taken
> in a working program, which is the case processors predict best, and
> the check is hoistable out of loops where the compiler can prove the
> range (the same analysis that removes bounds checks). So the
> answer to "what does the checking cost" is a measurement: chapter 21
> runs the comparison against C on a dated machine, prints the numbers
> CI produced, and names the cases where the check is still visible.
> What the decision buys is not in dispute: the alternative is
> arithmetic whose failures are undefined, and an
> undefined result is a bug that surfaces somewhere other than where it
> happened.

## 3.4 `match`, exhaustively

A `match` compares a value against patterns in order and takes the first
that applies. The exit codes from chapter 1 make a small table of one:

```wolf,run(exit=0)
fn label(code: int) -> str {
    match code {
        0 => "ok",
        2 => "rejected",
        3 => "trapped",
        4 => "unsupported",
        _ => "the program's own",
    }
}
fn main() -> !int {
    for code in 0..5 {
        print("{code} {label(code)}")
    }
    0
}
```

```console
$ lupin codes.lu
0 ok
1 the program's own
2 rejected
3 trapped
4 unsupported
```

The `_` arm matches anything and has to come last, because an arm after
it could never run. It is also the only reason this `match` compiles:
delete it, and the compiler produces a counterexample.

```wolf,fail(E0801)
fn label(code: int) -> str {
    match code {
        0 => "ok",
        2 => "rejected",
        3 => "trapped",
        4 => "unsupported",
    }
}
fn main() -> !int {
    print("{label(1)}")
    0
}
```

```diagnostic,from(book/ch03/s15)
error[E0801]: this `match` does not cover `1`
  --> ./s15.lu:5:5
   |
 5 |     match code {
   |     ^^^^^^^^^^^^
 6 |         0 => "ok",
...
10 |     }
   | ^^^^^ not every value is matched
   |
   = note: add arms for the missing cases, or end the `match` with a `_` arm to catch the rest
     deliberately.
```

`1` is a witness. The compiler did not say "this looks incomplete"; it
handed you a value your program has no answer for, which is a fact you
can check by hand and cannot argue with. A `match` on a `bool` gets the
same treatment with `false` as the witness, and the value the compiler
picks is always one of the cases you forgot. §2.4's `char` matches the
same way: literal arms, a witness for whatever they miss, and no set of
`'…'` arms the checker will ever count as complete.

Under the interpreter the same program starts, gets as far as the call,
and declines to invent an arm:

```console
$ lupin partial.lu
partial.lu: unsupported: no `match` arm applied; exhaustiveness is the type checker's
$ echo $?
4
```

That is the division of labor: totality is a static property, the type
checker owns it, and the interpreter refuses the program rather than
guessing which arm the author meant. Run the file through `wolf` and you
get the witness instead of the refusal.

Arms take more than one pattern when the answer is the same:

```wolf,run(exit=0)
fn main() -> !int {
    for code in 0..5 {
        let verdict = match code {
            0 => "the program's own",
            2 | 3 | 4 => "the toolchain's",
            _ => "the program's own",
        }
        print("{code} {verdict}")
    }
    0
}
```

```console
$ lupin verdicts.lu
0 the program's own
1 the program's own
2 the toolchain's
3 the toolchain's
4 the toolchain's
```

Two arms say the same words here, and that is a hint about the shape of
the data, not a flaw in the `match`: exit codes are not really one
number, they are a choice between "the program returned" and "the
toolchain refused". Chapter 6 gives that kind of choice a type of its
own, and the `match` that walks it gets its exhaustiveness checked the
same way this one does.
